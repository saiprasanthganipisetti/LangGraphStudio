Give your graph a useful memory

Explore what a graph remembers during one conversation, what it can retain across conversations, and how to store that information responsibly.

🧑🏻‍🚀
Byte says:

Think of short-term memory as the notebook for one ongoing conversation. Long-term memory is a carefully organised library that can be used again in future conversations. Let's decide what belongs where!

📝 Short-term memory

Thread-scoped

Stores conversation or workflow state for a particular thread. A checkpointer saves graph state at execution checkpoints so a conversation can resume with its earlier context.

  • Conversation messages
  • Current project request
  • Pending clarification
  • Current workflow step
In TeamPilot: remember the uploaded project brief and unresolved questions while the manager is working in the same project conversation.

📚 Long-term memory

Cross-thread

Stores selected information that should be available across separate threads or sessions. LangGraph Store organises memories by namespace and key.

  • Reusable team preferences
  • Approved project conventions
  • Technology decisions
  • Stable profile information
In TeamPilot: retain an approved team capability profile or a confirmed technology decision for later project conversations, subject to access controls.

🔍 Compare the two kinds of memory

QuestionShort-termLong-term
ScopeOne threadAcross threads
Typical mechanismCheckpointerStore
ExampleCurrent conversation contextApproved reusable team profile
LifecycleTied to thread/checkpoint lifecycleManaged independently by application policy

A checkpointer and a Store solve different problems. A checkpointer persists graph state; a Store persists application memories you choose to retrieve and update.

👤 Memory schema: Profile

A profile is a structured representation of relatively stable facts about one person or entity.

{\n "member_id": "member-01",\n "role": "Backend Engineer",\n "skills": ["Python", "FastAPI"],\n "interests": ["AI agents"],\n "learning_goals": ["LangGraph"]\n}

Useful when the application needs one coherent record that can be updated as facts change.

🗃️ Memory schema: Collection

A collection stores multiple independent memories or observations, each with its own identity and metadata.

[\n {"type": "decision", "text": "Use FastAPI"},\n {"type": "preference", "text": "Prefer small PRs"},\n {"type": "learning", "text": "Explore GraphRAG"}\n]

Useful when facts accumulate over time and should be searched, filtered, added or removed independently.

🛡️ Memory safety rules


  • Store only information the application genuinely needs.
  • Keep personal data scoped to authorised users and projects.
  • Record provenance, timestamps and confidence for extracted facts.
  • Ask for confirmation before saving uncertain or consequential profile changes.
  • Provide correction, retention and deletion workflows.
  • Do not treat model-generated guesses as verified team skills or availability.
