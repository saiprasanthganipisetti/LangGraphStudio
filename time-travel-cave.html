🕰️ TIME TRAVEL CAVE

Pause. Inspect. Change. Replay.

Learn how LangGraph checkpoints let a workflow pause for people, recover from interruptions, inspect earlier states and explore alternative decisions.

Byte says: “Imagine your graph leaves a trail of snapshots. You can pause at a checkpoint, ask your manager a question, fix a decision, or revisit an earlier point. The original history stays available while a new path branches off!”

🧭 The checkpoint trail

A checkpointer saves graph state at super-step boundaries. A thread_id identifies the conversation/workflow thread. Checkpoints make human-in-the-loop, recovery and time travel possible.

A checkpoint is a saved snapshot at a graph execution boundary—not a full copy of every Python variable or external system. External side effects need their own idempotency and recovery design.

⏸️ Static breakpoints

Configured when compiling/running the graph. Useful for debugging by pausing before or after named nodes.

TeamPilot example: pause before allocate_tasks to inspect the incoming state, or after it to inspect the proposed assignments.

🧑 Human interrupts

Call interrupt() inside a node to pause conditionally and request external input. Resume with Command(resume=...) using the same thread ID.

TeamPilot example: ask the manager to approve, reject or revise task owners before generating assignment emails.

🔁 What happens when an interrupt resumes?

  1. Graph reaches interrupt(payload).
  2. LangGraph persists the checkpoint and surfaces the payload to the caller.
  3. The application displays the approval form to the manager.
  4. Application invokes the graph again with Command(resume=decision) and the same thread_id.
  5. The interrupt call returns the decision to the node and the graph continues.
Important: the node containing interrupt() restarts from its beginning when resumed. Put the interrupt before non-idempotent side effects; do not wrap it in a broad try/except that swallows the pause exception.

🌀 Time travel: replay or branch?


Replay from a past checkpoint
Re-run from that saved state. The new execution creates a new branch of history; it does not erase the original.


Fork with edited state
Use update_state on a selected checkpoint, then resume from the resulting checkpoint to test an alternative.


For TeamPilot: revisit the allocation checkpoint, change one person's capacity or task owner, then replay validation to compare the new outcome. Never treat a replay as undoing an email or other external action already performed.



📨 Double-texting: what if a second user message arrives?
“Double-texting” describes a new user message arriving while a run/thread is still active. It is an application-level concurrency decision, not one universal automatic behaviour.


StrategyWhat it meansTeamPilot use


RejectTell the user the run is busy; ask them to retry.Simple first MVP.


EnqueueQueue the new message until the active run completes.Queue follow-up clarification requests.


InterruptStop or pause the active run, then process the new input.Manager says “stop allocation; new priority”.


RollbackResume from an earlier checkpoint and branch with the new input.Rework task allocation from a pre-approval snapshot.


Choose and implement the policy deliberately. Protect each thread from concurrent writes, define queue/locking behaviour, and guard external side effects against duplicate execution.
